# 服务器部署

前提：域名 `renjiahang1201.xyz` 的 A 记录指向服务器公网 IP，并开放 TCP 80、443、22。

## 首次迁移：Docker 运行环境

当前线上站点仍在运行时，**不要**直接执行 `docker compose up`，也不要先停止旧的 Node、Caddy 或 Nginx 服务。先确认它们分别占用了哪些端口，再安排一次短暂切换窗口。发布工作流也会在同步代码前检查 Docker、Docker Compose、`rsync` 与 Docker 权限；任一缺失会直接失败，当前网站不会被改动。

服务器为 Ubuntu 24.04 时，可先将仓库中的安装脚本复制到服务器，再以 root 执行（将 `deploy` 替换为 GitHub Actions 使用的 SSH 用户）：

```bash
sudo bash provision-docker-ubuntu.sh deploy
```

脚本仅安装 Docker Engine、Compose Plugin 与 `rsync`，并将部署用户加入 `docker` 组；不会停止现有网站或绑定 80/443。执行后需要重新登录 SSH。Docker 官方建议生产环境通过其 APT 仓库安装，而非 convenience script。[Docker Ubuntu 安装说明](https://docs.docker.com/engine/install/ubuntu/)

在服务器执行：

```bash
git clone https://github.com/JiahangRen/btc-usdt-long-short-indicator.git
cd btc-usdt-long-short-indicator
docker compose up -d --build
```

Caddy 会自动申请并续期 HTTPS 证书，站点地址为 `https://renjiahang1201.xyz`。

## 云端 24 小时提醒（多用户）

生产部署会同时启动 PostgreSQL、Redis 和 `alert-worker`。在服务器项目目录复制 `.env.example` 为 `.env`，填入仅保存在服务器上的随机值：

```bash
cp .env.example .env
openssl rand -base64 32
```

将生成的 Base64 值填入 `ALERT_ENCRYPTION_KEY`，并为 `POSTGRES_PASSWORD` 设置独立的高强度随机密码；两者绝不能提交到 Git、粘贴到工单或发送给用户。应用会用 AES-256-GCM 加密存储每位用户的 SendKey，关闭网页后由 worker 保持 OKX 行情订阅、判定规则并经 Redis 队列调用 Server酱。

首次启用后，在网页“云端 24 小时提醒”板块注册账户并保存 SendKey。用户可自行删除规则、SendKey 或账户；删除账户会级联删除对应的凭证、规则和发送记录。

`alert-worker` 的日志应持续可见；如果它未运行，网页规则仍会被保存，但不会在关页后触发。不要将 PostgreSQL 或 Redis 端口暴露到公网。

## 个人微信消息推送

网页底部的“消息推送”板块支持多条 BTC 上涨、下跌及多／空爆仓价提醒。每位访问者在自己的浏览器中填写 [Server酱 SendKey](https://sct.ftqq.com/sendkey/)；SendKey 和规则只保存在该浏览器的 `localStorage`，不会发送到本站服务器、写入 SQLite 或提交到 Git。

页面打开时每秒检查一次已经加载的 OKX 行情，并在价格穿越阈值时直接向 Server酱发起推送。重复提醒的每条规则可单独设置触发冷却时间；仅提醒一次的规则不使用冷却时间。测试当前市价会发送实时价格；测试当前规则会按正在编辑的目标价发送且不会保存规则。推送会同时提交精简的 `short` 卡片摘要，让目标价格优先出现在微信通知卡片中；消息通道仍可能添加“设备收信”等自身前缀。浏览器标签页关闭、设备休眠或清除站点数据时，本地提醒将不会运行；若需要 24 小时后台提醒，应使用独立服务并把 SendKey 安全保存在自己的服务器密钥管理中。

启用性能面板：

```bash
docker compose --profile monitoring up -d
```

不要将 Netdata 端口暴露到公网。在本地 Mac 创建隧道后访问：

```bash
ssh -L 19999:127.0.0.1:19999 root@服务器IP
```

然后打开 `http://127.0.0.1:19999`。

## GitHub 推送后自动部署

仓库包含 `.github/workflows/deploy.yml`。向 `master` 推送后，GitHub Actions 会通过 SSH 将代码同步到 `/opt/btc-usdt-long-short-indicator`，构建新版镜像、检查本机与公网健康接口。服务器需要安装 `rsync`：

```bash
apt-get install -y rsync
```

建议使用专用部署账号；首次配置也可使用现有服务器账号。在部署客户端生成一对独立的 Ed25519 密钥，将公钥追加到服务器账号的 `~/.ssh/authorized_keys`，私钥只保存到 GitHub Actions Secret。

在仓库 `Settings → Secrets and variables → Actions` 中创建：

- `DEPLOY_HOST`：服务器 IP。
- `DEPLOY_USER`：SSH 登录用户名。
- `DEPLOY_SSH_KEY_B64`：独立部署私钥经过 Base64 编码后的单行文本。在服务器执行 `base64 -w 0 /home/deploy/.ssh/github_actions` 获得。

工作流不会把 GitHub Token 保存到服务器。服务器上的 `.git`、`data/`、`.env` 不会被同步删除；其中 `.env` 必须在首次部署时由服务器管理员创建并妥善备份。

### 自动回滚

每次发布前，工作流会把当前应用文件复制到 `/opt/btc-usdt-long-short-indicator-releases/`，并记录最新回滚快照。新版会先完成镜像构建，再替换 `app` 与 `alert-worker`；若容器健康检查、本机 API 检查或 GitHub Actions 的公网 HTTPS 检查失败，工作流会自动恢复最近一次快照并重启上一版容器。

这是一套“自动恢复”机制，容器切换时仍可能出现数秒短暂 502。要实现真正无感的蓝绿发布，需要先将当前可写的 SQLite 行情目录从应用实例中独立出来，再部署两套隔离的应用容器并由 Caddy 在健康检查通过后切换流量；在此之前，不应让两个实例同时写同一 SQLite 目录。
