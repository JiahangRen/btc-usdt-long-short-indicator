## 3. P0：必须先修的 4 个问题

### P0-1 ✅ 日线数据自 2026-08-31 起冻结 → 1d 窗口永久死锁 → 候选模型永久锁死

**证据链（逐环可复现）：**

1. `data/market.sqlite` → `candles` 表：`coinbase / 1d` 共 1000 根，**最后一根 = 2026-08-31 00:00**，`updated_at = 2026-08-31 10:50`（已 20 天未更新）。
2. 根因在 `server.mjs:1923 forecastHistory`：
   ```js
   const stored = storedCandles(source, interval, 1000);
   if (stored.length >= 900) return { candles:stored, ... }; // 条数够就当"新鲜"，直接返回
   ```
   日线只被研究模块消费，而研究模块因为"条数够"永不回源 → **自我强化型冻结**。注意 `research?refresh=1`（页面"更新研究"按钮）也不会绕过这层。
3. 因日线冻结，`targetAt = 最后日线时间 + 1 天` 恒为 2026-09-01，`bucket_at` 恒为 2026-08-31 00:00，撞上 `UNIQUE(bucket_at, horizon_key)` → **1d 的 `research_predictions` 全库只剩 1 行**（实测 n=1, settled=0）。
4. 结算找不到 `time >= target_at` 的日线 → 1d 永远"待结算 1"。
5. `compareCandidateToBaseline` 的 `enough` 要求**四个周期**都 ≥30 个配对样本，1d 恒为 0 → `readyForNext` 永远 false → `candidateLocked=true` → **"训练下一候选"按钮永久 disabled**（截图里那颗灰按钮就是它）。
6. 实测 `training.shadow.reason` = "每个周期需 30 个已配对结算样本；当前样本不足"，而真实情况是 15m/1h/4h 各有 **375/375/369** 个配对样本，只有 1d 是 0 —— 提示语完全没指出是哪个周期卡住。

**附带影响**：1d 卡片上显示的"匹配质量 32% · n=364/428"是基于**截至 8 月 31 日的日线**算出来的，但价格区间却用当前价（$81,791）缩放 —— 卡片看起来是"实时"的，实际历史基准已经过期 3 周。

**修法**：`forecastHistory` 增加"末根 K 线时效"判据（如 `now - lastCandleTime > 2 * intervalMs` 就回源），而不是只看条数；并给 1d 单独的采集保障（服务端定时器写 1d 预测，见 P0-4）。

---

### P0-2 重叠持仓被当成"顺序交易"复利 → 净收益与最大回撤被放大 2×～12×

- 预测每 15 分钟写一条，但 1h 的持有跨度是 60 分钟、4h 是 240 分钟 → **同一 15 分钟格里有 4 个 / 16 个并发持仓**（实测：1h 持仓 60 分、步长 15 分；4h 持仓 240 分、步长 15 分）。
- `researchScorecard`（`server.mjs:2130-2131`）与 `pairedPredictionMetrics`（`2078-2083`）都按 `equity *= 1 + value` 逐笔连乘 —— 等价于假设"同一时刻只持一个仓、按顺序执行"。
- **实测放大倍数**（无条件全做多、含成本，同口径对比）：

| 周期 | 重叠口径 | 非重叠抽样口径 | 放大 |
|---|---|---|---|
| 1h | −10.34%（377 笔） | −4.98%（95 笔） | ≈2.1× |
| 4h | −13.24%（371 笔） | −1.06%（24 笔） | ≈12.5× |

**推论**：页面上"成本后净收益 −9.08% · 最大回撤 −11.14%"（4h）**不是任何可执行策略的盈亏**。同时，4h 的独立样本数其实只有 ~24 个，而不是 371 个 —— 所有记分卡指标的实际信息量比显示的小一个数量级，置信区间应基于有效样本数而非行数。

**修法**：经济指标改为"按 bucket 网格对齐持仓"的口径（同一格内多笔按名义仓位加权平均，或强制每隔 `hold/15min` 个格才允许开新仓），并在 UI 上同时给出"重叠口径 / 非重叠口径"两个数字。

---

### P0-3 缺少"不交易"与 buy&hold 对照 → 用户无法判断信号是否有价值

实测：模型成本后净收益 −1.27% / −8.30% / −9.08%，而"完全不交易"= 0.00%。**三个周期都跑输"什么都不做"**，但页面上没有任何基准行，用户看到的只是一串负数。

**修法**：记分卡每条周期加三行对照 —— ① 不交易（0%）② 无条件全做多（同口径含成本）③ 随机/常数 0.5 概率策略。这是让"模型有没有用"一眼可判的最低成本改动。

---

### P0-4 预测采样由"谁打开网页"驱动，桶覆盖率仅 ~20%

- 预测写入发生在 `researchOutlook()` 内部（`server.mjs:2185 storeResearchPrediction`、`2186 recordCandidateShadowForecasts`），即"有请求才有样本"。
- 实测：15m 的 `bucket_at` 覆盖 2026-08-31 11:15 → 2026-09-19 17:15，共 **1850 个 15 分钟格，只落了 378 行（20.4%）**；相邻桶步长集合是 `15/30/45/60/75/90` 分钟，缺口明显。
- 后果：已结算样本是**便利样本**（夜间/无人开页面时缺样本），命中率、Brier、ECE、经济指标全部建立在这个有偏子集上。这也意味着"样本量够了"这件事永远不会按预期推进。

**修法**：把"按 15 分钟桶生成预测 + 结算"移到服务端 `setInterval` 定时任务，与 HTTP 请求解耦；页面只读结果。

## 4. P1：模型层面

### 4.1 概率被压缩成常数 0.5，模型实质退化

- `mean|p − 0.5|`：15m **0.0304**、1h 0.0367、4h 0.0483 → 概率几乎恒在 0.46–0.53。
- 这正是 BSS≈0、AUC≈0.5 的直接原因，也是"实时命中 49.1%"这种噪声级数字的来源。
- **候选模型更极端**：A/B 配对样本里 15m 的 `coverage = 0.53%`（375 笔里只有 **2 笔**交易），基线是 6.93%（26 笔）。而 A/B 面板把"成本后净收益"作为升级门槛之一 —— **用 2 笔交易的收益去当门槛，统计上无效**。

### 4.2 近邻软加权带宽过宽 → 退化成无条件均值

`historicalProjection`（`server.mjs:2000-2002`）用 `scale = 35 分位距离`、权重 `exp(−d/scale)`，而报告出来的"有效样本数 = 1/Σw²"是 **717 / 910（79%）、364 / 428（85%）** —— 权重几乎均匀，**距离度量基本没起作用**，"历史近邻"实际上接近"直接取全历史均值"。这就解释了为什么它没有边际信息。

**修法**：带宽用交叉验证选（最大化样本外 Brier）或改成按验证集选 k 的 k-NN；报"有效样本份额"作为诊断指标；顺便把"匹配质量 30%"改名为"邻域紧致度"并提供校准曲线（按匹配质量分桶看实际命中率），否则用户会把它误读成准确率。

### 4.3 未经验证就生效的"魔法数"清单

下面这些常数直接决定输出，但代码里没有任何验证产物支撑（而 UI 文案却说"短周期仅在可验证特征上加权"）：

| 位置 | 常数 |
|---|---|
| `2164` | 新闻权重 0.25/0.12、情绪 0.08/0.04、微观结构 0.14/0.12/0.09/0.025 |
| `2171` | `analogueWeight = range ? 0.62 : vol>0.006 ? 0.42 : 0.48` |
| `2173` | logit 空间位移 `news*0.22 + sentiment*0.12 + micro*0.18` |
| `2160` | 各周期收益上限 `cap = 0.015 / 0.03 / 0.05 / 0.12` |
| `2052` | 三重屏障 `unit = σ·√h·1.15` |
| `2070` | `treeWeight = (|trend|>1.1 || vol>0.006) ? 0.62 : 0.5` |
| `2063/2071` | 学习率 .012/.018、epochs 180/220、树 24 轮、shrinkage .14 |
| `1996` | 近邻距离四维权重 20/12/18/8 |
| `1939-1940` | 新闻正/负词表 |

**修法**：抽成单一 `researchConfig` 对象（带版本号与注释），每次改动可审计；并对每一项做一次"关掉它 vs 打开它"的消融实验，把结果落到记分卡里。

### 4.4 标签与评估的细节问题

- **三重屏障丢弃歧义样本**：`up && down` 同 bar 触发时直接 `return null`（`2053`），系统性剔除了高波动样本 → 训练集偏向低波动 regime。15m（horizon=1，只看下一根）尤其严重。应报告"标签覆盖率"，或对歧义样本改用更细粒度价格判定。
- **BSS 基准口径混用**：`trainFusionModel` 用**训练集**上涨率（事前，合理），`researchScorecard` 用**已结算样本自身**上涨率（事后）。两处口径不同，事后口径会让 BSS 显得更好看。建议统一为"事前可得的滚动基准"（如过去 N 天上涨率）。
- **稳健性门槛不一致**：`compareCandidateToBaseline` 用"样本 ≥10 的市场状态"，`abComparison` 用 `minSamples=30`。同一件事两套标准，会出现两份互相矛盾的结论。
- **无多重比较控制**：4 周期 × 3 regime × 多条门槛，在零假设下"蒙到一个绿灯"的概率很高。建议：预先指定唯一主周期（`primary` 字段已经算了但前端从未使用，`const primary=windows[2]`），其余为次要；门槛改为带 bootstrap 置信区间的判据（如"净收益 95% CI 不含 0"），而不是"≥ 阈值 3%"。
- **Platt 校准窗偏窄**：~190 样本拟合 2 参数可接受，但 4h 的 ECE 19.1% 说明校准窗 regime 与部署期不一致。建议滚动校准或按 regime 分层。
- **无模型持久化**：`research_training_runs` 只存指标，`trainFusionModel` 每次请求从头重训。**"建议人工复核"之后没有可执行的切换路径**（权重全硬编码在 `researchOutlook` 里），所以 A/B 面板给出的 green 其实无法落地。建议把候选模型权重（weights/bias/slope/intercept/trees）序列化入库，并让 `researchOutlook` 从库里读参数。

## 6. 建议的推进顺序（最小可行改动）

1. **修 `forecastHistory` 时效判据** → 日线恢复更新，1d 解冻（P0-1）。同时给 1d 单独加"日线未更新则跳过并在 UI 标注 stale"的保护。
2. **把预测生成/结算挪到服务端定时器**（P0-4）。这一步同时修好了 1d 桶问题与样本偏差。

## 7. 一句话总评

模型的**特征工程和验证脚手架（三重屏障 + 时间序切分 + embargo + 配对影子结算 + BSS/ECE/AUC）设计得比一般个人项目规范得多**，问题是三处断点让它失去意义：**日线冻结导致 1d 链路死锁、采样依赖访问导致样本有偏、经济指标口径不可实施**；再叠加概率被压缩到 0.5 附近，最终呈现出"验证做得很全，但结论是模型没有增量信息、且成本后必亏"的局面。先把 P0 四项修完，记分卡才第一次真正有意义。
